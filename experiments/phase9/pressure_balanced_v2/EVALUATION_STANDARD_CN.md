# 压力迁移系统评价标准

记录日期：2026-10-16。适用于后续 TP1/TP4 压力迁移 pilot 与返回数据分析。
评价对象是整个实例池；TP1/TP4 的分项指标用于解释结果，不能用迁移请求
本身变快或单端提升替代整个池的收益。以下是离线评价标准，不改变调度策略。

## 1. 主结果：吞吐与延迟分别报告

- 原始输出吞吐：固定窗口内实际向客户端交付的输出 token 数 / 窗口秒数。
  不计 prompt token，不将窗口外 drain token 加入分子。
- 延迟：TTFT、TPOT、E2E、超过 100 ms 的输出间隔比例、最大输出间隔。
  给出分布、尾部和请求长度分组；迁移接缝属于真实输出间隔，不能删掉。
- 在固定 GPU 数量、模型、请求内容和长度分布下，比较不同到达率的吞吐与延迟。
  保留排队量、抢占和负载覆盖情况，持续积压的结果不当成稳定服务容量。
- 机制指标：每次迁移的 handoff、START 到源 KV 释放耗时、迁移次数、目标影响、
  搬运和额外显存开销。瞬时吞吐仅用于解释行为，不以选取峰值代表整体收益。

## 2. 保留现有软惩罚 goodoutput

对请求 i，令 f_i 为完整请求中超过 100 ms 的输出间隔比例，m_i 为最大间隔秒数：

    w_i = min(1, 0.01 / f_i, 1 / m_i)
    G_soft = sum(窗口内请求 i 的输出 token 数 * w_i) / T

分母为零的惩罚项按 1 处理。保持当前实现：完整请求的质量权重作用于该请求
窗口内全部输出，包括 drain 阶段发生的违约；drain token 本身不计产出。
这是项目自定义的连续效用指标，不称为论文通用的硬 SLO goodput。
不得在看到结果后修改惩罚参数来改变结论；若另行比较参数，完整报告敏感性。

## 3. 新增请求级 SLO 达标率

当前定义为“输出流 SLO”，不是完整交互 SLO：

    pass_i = (f_i <= 1%) AND (m_i <= 1s)
    attainment = 达标请求数 / 被评价请求数

100 ms 本身不属于超过 100 ms；比例正好 1%、最大间隔正好 1 s 均允许。
TTFT 和排队时长尚未定门槛，继续画曲线，不纳入 pass_i。TPOT 单独报告，
不将平均 TPOT <=100ms 与本项目的慢间隔比例规则混用。

请求集合按实际开始时间落在测量窗口内确定；质量检查覆盖其完整输出，
包括测量窗口后收尾。晚于窗口才实际启动的请求单独计数，不悄悄并入分母；
其到达迟延仍使对应实验对照可能无效。未完整收尾、失败、输出缺失是技术失败，
不能从达标率分母删除后宣称成功。时间窗口内尚未完成不等于请求最终不达标。

必须同时输出：

- 全部请求达标率。
- 多 token 请求达标率（至少一个输出间隔），重点用于分析 decode/迁移效果。
- 单 token 请求的数量与单列结果：没有输出间隔，当前规则自然通过，不能当成
  decode 健康证据。prefill 竞争流中大量单 token 请求会抬高总体达标率。
- 按初始路由 TP1/TP4 分组，必要时按长度和迁移状态进一步分析。初始路由分组
  不代表迁移后每个 token 的实际执行归属；池内 token 归属仍按真实交付来源统计。

## 4. 补充硬 SLO goodput，避免窗口口径混淆

- 请求 goodput：上述请求集合中，达标且在窗口结束前完成的请求数 / T。
- 输出 token goodput：完整输出流 SLO 达标的请求在窗口内交付的 token 数 / T。
- 达标率与请求 goodput 不可混同：窗口后完成的请求仍参与完整质量评价，
  但不计入窗口内完成请求吞吐。单 token 流另列，不能据总体数值判断 decode 收益。

输出文件：`sustained_goodoutput.json` 保存逐请求及聚合指标，
`comparison_metrics.json` 保留请求延迟和到达检查，`scene_results.json` 与
`pair_acceptance.json` 汇总 STAY/迁移的吞吐、软得分、达标率和硬 goodput。
原始日志足以对已经启动的旧版本实验离线补算，不必为了新增评价字段重跑 GPU。

## 5. 实验有效性与结论

同一对照使用相同输入、随机种子、到达序列与服务配置。保持当前到达误差检查；
持续负载收益还要求两臂实际负载覆盖达标。保留停顿、无迁移和覆盖不足场景，
不混合无效对照计算平均提升。轻载、目标繁忙、KV 紧张场景先验证功能与安全。
既要报告收益，也要报告其代价；得分相同并不排除延迟曲线或资源余量不同。

参考评价路线：GoodServe 用 E2E 达标请求/s；Nitsum 用同时满足 TTFT/TPOT 的
请求/s，并扫描到达率；Gyges 分别报告 tokens/s、TTFT/TPOT 及转换开销。
本项目采用吞吐与延迟主结果，加软得分和硬 SLO 达标率的组合，三者同时保留。
