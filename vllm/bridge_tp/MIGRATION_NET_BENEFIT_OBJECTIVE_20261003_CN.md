# TP1→TP4 迁移收益函数与验证顺序

日期：2026-10-03。状态：设计与校准计划；**尚未作为在线迁移决策器上线**。

## 1. 决策对象

每个完成 prefill、仍在 TP1 的候选请求，在控制 tick 比较以下动作：继续留在 TP1；在将来的某个候选启动点开始 Shadow，并选择 LOW/MEDIUM/HIGH 初始速率。每次重新观测后可以重新评估。Shadow 已经安全 ready 时按现行 M3 规则尽早提交；收益比较决定是否启动，不延迟已就绪的安全提交。冻结前的 M4 取消另作决策。

TP4 忙、请求已输出超过 1000 tokens、预测为长请求，都只是状态或收益估计的输入，**不是独立的迁移开关**。当 TP4 繁忙、TP1 足以安全完成时，迁移造成的 TP4 干扰通常使净收益为负；当 TP4 空闲、TP1 承压且锚请求还很长时，净收益可能为正。这两种结论必须由同一函数算出。

## 2. 目标函数

在固定硬件、同一请求到达流及同一时间窗口内，以继续留在 TP1 为基线。定义系统损失：

```text
L(a) = E[Σ_i w_i · (completion_i(a) - arrival_i)]
     + λ_slo · E[Σ_i v_i · SLO_violation_i(a)]
     + λ_fail · E[Σ_i u_i · failure_or_preemption_i(a)]
     + λ_tail · E[terminal_unfinished_work(a)]

Δ(a) = L(STAY) - L(a)                  # 正值表示迁移更好
a*   = argmax_{a∈可行方案∪{STAY}} LCB_α[Δ(a)]
仅当 LCB_α[Δ(a*)] > C_min 时启动；否则 STAY。
```

`i` 包括锚请求、TP1 peers、TP4 现有请求及观察窗口中的后续到达请求。`w_i` 表示服务权重，默认先统一为 1；SLO、失败及未完成工作的权重必须事先固定，不能看完结果再调。`terminal_unfinished_work` 防止只看短窗口时把代价移到窗口外。这里不再额外叠加“锚请求加速”“TP1 KV 释放”“TP4 干扰”等单独分数：它们已经通过各请求的完成时间、SLO 和后续准入计入，重复相加会双重计数。若运行时间窗口不足以测后续准入，用校准的 TP1/TP4 KV 机会成本作**临时代理量**，且须标明代理与真实收益的差异。

`LCB_α` 是由配对实验或经验证的预测模型得到的保守下界，承担测量噪声及长度分布不确定性。没有足够数据时，该值为 `UNKNOWN`，不假造零方差；正常负载下维持 STAY 并记录候选动作。`C_min` 包括控制开销和模型误差缓冲，待独立数据标定，当前不指定经验常数。

OOM 风险不能用“锚请求为长请求的概率”代替。真实 OOM/抢占损失应由源池所有请求、未分配 prefill、未来到达及保护动作共同估计；短期内用可靠的源池 guard 作可行性约束，暂不声称已有 `P_pool_oom`。

## 3. 可行方案与安全约束

每个候选动作需满足：源端和目标端遥测新鲜；源池可用余量 `H = F - G - P` 按**分离的持续 decode 增长**预测，并计入未分配 prefill 预留；TP4 的请求 KV 容量与 guard 足够；迁移 channel 可用；四 rank 的历史、delta、readback 与安全边界仍满足现有门禁。`P` 不重复计入已经完成 prefill、已实际占用的 KV。

用当前上下文、速率、delta、候选点等待、尾部同步、handoff 到**TP1 KV 真正释放**估计 `T_release(a)`，而非只算历史传输完成。若 `T_guard` 与 `T_release(a)` 的保守区间重叠，普通收益优化不得把这个动作标成安全；需要容量保护或单独的紧急路径。紧急时允许选择预期损失最小的可行动作，但不能跳过四 rank ready，也不能将最高速仍赶不上的情形称为“已救援”。目标负载影响预测的 TP4 排队/TPOT/干扰成本；只有物理 KV 不足或系统安全门禁失败才直接排除目标。

## 4. 如何计算长度不确定性

预测器给出条件剩余输出分布 `p(R | 当前请求状态)`，按当前 `max_output_tokens - generated_tokens` 和真实停止规则截断。自然 EOS 与 `ignore_eos=true` 分开处理。对于每个候选启动点和速率，以该分布积分：

```text
E[Δ(a)] = Σ_r p(R=r | state) · [L(STAY,r) - L(a,r)]
```

准备期间 TP1 仍生成的 token、请求可能在 Shadow 中结束、M4 取消与 TP4 接管后的剩余工作，都应进入情景模型。输出超过 1000 tokens 仍能开始迁移的实验，需把请求 `max_output_tokens` 设为超过 1000；现有 1024-token 上限轨迹不能检验这种情景。为避免把强制长输出当作自然结束证据，`ignore_eos` 压力轨迹只校准传输和容量，收益评估另用自然 EOS 轨迹。

## 5. 校准顺序和验收

1. **先补测量**：记录每 tick 的源池余量、decode 增长、prefill 预留、TP4 负载/排队、预测分布、各挡位有效速率、候选点到 TP1 KV 释放的各阶段时间，以及所有请求的完成时间、ITL、抢占和后续准入。
2. **再做同机配对**：相同到达流、交错运行 STAY 与不同启动点/速率的 MIGRATE；包括 TP4 繁忙/空闲、TP1 高/低负载、自然短/长输出，以及已生成超过 1000 tokens 的场景。对照代码 HEAD、模型、原始输入 SHA、GPU 身份与请求随机种子。
3. **拟合与验证**：先用上述完成时间计算离线 `Δ`，分状态检验符号和误差；留出不同负载与长度分布做验证。比较“现在迁”“晚一点迁”“留 TP1”，报告选择后总损失、SLO/抢占、误迁、漏迁及置信下界覆盖率。
4. **先只影子回放**：收益函数缺少有效输入时写 `UNKNOWN`；与现行 M1 决策并行记录，不直接驱动线上 Shadow。只有独立轨迹上的正净收益及安全门禁都通过后，再考虑接入 START。

当前 A100 晚启动实验只有一次，且锚请求 `ignore_eos=true`、上限 1024、严格 ITL SLO 未通过。它证明了晚启动物理机制可行，并暴露旧 M1 容量估计偏差；**不能用来确定收益函数权重或最优启动时刻**。
