# BridgeTP 评测 SLO 标准 v6（长度感知 TTFT）

日期：2026-10-04。状态：**口径已定；指定 A100 GPU UUID 集合的 TP4 TTFT 参考表已冻结，v6 正式负载评测尚未完成**。冻结数值见 [`experiments/phase9/slo/slo_v6_a100_tp4_reference_20261004.json`](../../experiments/phase9/slo/slo_v6_a100_tp4_reference_20261004.json)。本标准用于同一 Qwen2.5-14B 模型、同一五张 A100-PCIE-40GB、同一请求到达流下的系统比较；更换物理 GPU 集合须重新校准或另列场景。旧 v1–v5 审计结果保留原始版本名，不追溯改写。

## 1. 请求和时间的定义

- `L` 是进入系统时由冻结 tokenizer 得到的**原始输入 prompt token 数**，包含系统提示、历史对话等实际送入模型的 token。比较双方使用同一个 `L` 和同一个长度档。前缀缓存命中量另行报告，不能因某系统缓存命中而改变该请求的 SLO。
- TTFT 从外部请求发出到客户端收到第一个完整输出 token 计算，包含排队、prefill、网络/代理和首次输出；不得仅计算 GPU prefill 时间。
- TBT/ITL 是客户端可见的相邻输出 token 时间差。请求 mean TPOT 是所有 TBT 的平均值；单 token 输出没有 TBT 样本。
- 迁移锚请求只统计客户端统一流一次；失败、超时、取消和实验窗口末尾未完成的请求计入分母、不能算 SLO 合格。保存实际输出长度、结束原因、token 时间戳和到达时间。

## 2. TTFT：随原始输入长度变化

| 报告长度档 | 原始输入 token 数 | TTFT 合格门槛 |
| --- | ---: | --- |
| B1 | 1–512 | `B95(L) + 1000 ms` |
| B2 | 513–2048 | `B95(L) + 1000 ms` |
| B3 | 2049–4096 | `B95(L) + 1000 ms` |
| B4 | 4097–7168 | `B95(L) + 1000 ms` |

`B95(L)` 是预先指定的**同一个参考实现**在热机、无排队、无其他请求时的 TTFT P95 随输入长度的曲线。建议以原生 vLLM、冻结模型/精度/配置、固定 TP4 为参考，在 128、512、1024、2048、4096、6144、7168 token 七个锚点测量；每点至少 30 次独立请求，分不同启动轮次重复。各点 P95 先做非递减约束，再在相邻锚点间线性插值；短于 128 token 使用 128 点门槛。保存原始时间戳、prompt、配置、HEAD 和输入 SHA。报告分档用于呈现结果，**实际判定按每条请求的 L 插值**，不会给 513-token 请求套用 2048-token 的完整预算。参考实现只用于制定共同门槛，不是每个被测系统各自的基线。1000 ms 是预先给定的排队预算，校准后不得按哪组结果更好再修改。当前 8192-token 上下文且预留最多 1024 输出 token 时，输入超过 7168 token 不属于本表；改变上下文或输出上限需另设场景。

本次参考表用两轮共 210 条独立请求校准七个锚点，每点 30 条。2048-token 的 `B95` 为 718.7 ms；相同 GPU UUID 门禁下、1024-token 输出上限的复核单请求 TTFT 为 739.3/738.2 ms，说明输出上限从 16 增至 1024 不能解释旧探针 1026/1027 ms 与本次约 0.72–0.74 s 的差异。旧探针未保存 GPU UUID，差异原因仍未定位，因此参考表仅适用于记录的 GPU 集合和配置。复核压缩包的 preflight 只保存 GPU 名称；UUID 由运行指令先行核对，后续采集应把 UUID 也写入包内。缓存命中、不同任务类型或不同模型若改变基线，应另设场景并分别冻结，不能在同一比较中混用门槛。

## 3. 流畅性、完成和迁移停顿

主档请求合格需同时满足：

1. 已完成，且 TTFT ≤其长度档门槛；
2. 请求 mean TPOT ≤100 ms；超过 100 ms 的可见 TBT 比例 ≤1%；
3. 任一可见 TBT ≤1000 ms；迁移锚请求的客户端可见 handoff ≤1000 ms。

50 ms mean TPOT 与 50 ms 慢间隔门槛保留为**严格档敏感性分析**，不能与 100 ms 主档结果混称。1000 ms 来自现有 handoff 合同上限，既单独约束 handoff，也约束所有请求的最长可见停顿；因此非迁移的长 prefill 导致 >1 s 输出停顿仍会被判失败。报告最大 TBT、超过 200/500/1000 ms 的间隔比例与次数、P95/P99 TBT，以及 handoff 的中位数/P95/P99/最大值。handoff 是独立机制指标，不能代替客户端可见流畅性。

旧的固定 60 s E2E 门槛不进入 v6 主判定：可变输出长度下它会天然惩罚长输出。E2E 分布仍报告；实验请求超时、输出上限和观察窗口须在两组一致且提前记录。单 token 输出只适用 TTFT/完成条件。自然 EOS 与 `ignore_eos=true` 的合成压力工作负载必须分表报告。

## 4. 系统层面的比较

在同一到达流、负载和完整观察窗口内，并列报告：

- 原始吞吐：所有已完成请求数/s、输出 token/s；
- SLO 达标率：合格请求数 / **所有到达请求数**；
- 合格请求 goodput（requests/s）和合格输出 GoodOutput（tokens/s），共同分母为从首个请求到达到最后请求完成或统一截断的墙钟时间；
- TTFT 按长度档的分布与达标率、mean/P99 TBT、最大停顿、handoff、OOM/抢占/取消/超时。

主容量点为负载扫描中仍有 **≥95% 请求达标**的最大可持续到达速率；另报 ≥90% 容量点以便与采用 90% attainment 的论文比较。两者都必须在实验前固定；不能为了让某次结果“几乎全过”回头放宽门槛。样本量至少数百个独立请求，交错重复 STAY/MIGRATE 和不同负载；13 请求的接线烟测不足以推断 95% 容量。所有被测系统使用同一模型、硬件预算、请求集、到达时间、tokenizer、SLO 表和负载扫描规则。

## 5. 启用门禁与实施顺序

1. 修复现有 STAY/MIGRATE 比较器读取路径，**先对已拿回的两份 W2 包做只读审计**，确认两臂的请求、时间戳和输出完整；运行器 PASS 不能替代整池 SLO 审计。
2. 已用冻结输入在五 A100 机器上校准七个长度锚点，保存原始样本、机器、HEAD、模型/配置/输入 SHA，并以相同 UUID 门禁完成 2048-token 长输出复核。正式配对必须核对上述冻结表的适用范围；后续运行器应将 GPU UUID 写入压缩包 preflight。
3. 审计器新增 v6：按原始 prompt 长度查 TTFT 门槛、以 100 ms/1%/1000 ms 判定流畅性；旧 v5 原样保留。缺少长度或时间戳时报告不可计算，不猜测成功。
4. 先在低、中、高三个到达速率完成少量端到端试运行，再做足量、交错重复的 STAY/MIGRATE 配对和负载扫描。A4-P 的固定 1024-token 输出继续用于机制压力检查；自然 EOS 负载用于论文主比较与收益函数拟合。
5. 在同一冻结 SLO 下比较 95%/90% 容量点、原始吞吐、合格 GoodOutput、各长度档 TTFT 与停顿尾部。若长 prefill 导致的 >1000 ms 暂停仍出现，应独立测 TP4 调度预算，不通过事后放宽上限掩盖。

## 6. 文献定位

[DistServe（OSDI 2024）](https://www.usenix.org/system/files/osdi24-zhong-yinmin.pdf)按应用改变 TTFT/平均 TPOT 门槛，并以 90% 达标率附近的最大服务速率比较系统；[Sarathi-Serve（OSDI 2024）](https://www.cse.iitd.ac.in/~rijurekha/col851/scheduling_oct23_oct25/2024_osdi-sarathiserve.pdf)同时测严格/宽松的 P99 TBT 容量；[Mooncake](https://madsys.cs.tsinghua.edu.cn/publication/mooncake-a-kvcache-centric-disaggregated-architecture-for-llm-serving/ToS2025-Qin.pdf)按场景使用 100/200/300 ms TBT 门槛。v6 的 100 ms mean TPOT、1% 慢间隔和 1000 ms 最大停顿是 BridgeTP 的**预注册候选合同**，并非宣称三篇论文都使用了这一组合。
